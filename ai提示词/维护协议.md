# 长任务上下文持久化协议

这是一个可能持续很长时间、超过单个上下文窗口容量的大型任务。

你的上下文可能会被压缩、截断、总结或重新加载。为了避免重要信息在上下文优化过程中丢失，你必须维护一个外部持久化文档：

`PROJECT_CONTEXT.md`

该文件是本任务的**长期记忆 / 外部上下文 / 状态真源之一**。

你不能假设当前聊天上下文会永久存在。任何未来仍可能影响判断、实现、调试、验证或决策的信息，都应该及时写入该文件。

---

## 1. 每次开始工作时

如果 `PROJECT_CONTEXT.md` 已存在：

1. 首先读取它。
2. 将其中的信息视为当前任务的重要历史上下文。
3. 再结合当前用户要求、代码、文件和最新实验结果继续工作。
4. 如果文档内容与当前实际代码/文件冲突：
   - 以当前可验证事实为准；
   - 同时立即修正文档中的过时信息。
5. 不要因为当前上下文中没有提到某件事，就默认它没有发生；先检查 `PROJECT_CONTEXT.md`。

如果该文件不存在，则创建它。

---

## 2. 必须主动维护，而不是等用户提醒

在以下情况发生后，应更新 `PROJECT_CONTEXT.md`：

- 完成一个重要阶段；
- 修改了总体方案或架构；
- 做出了会影响后续工作的设计决策；
- 找到了重要 bug 或根因；
- 排除了一个看似合理但实际错误的方向；
- 修改了关键代码、接口、数据结构或配置；
- 得到了重要实验结果、benchmark、综合结果或测试结果；
- 用户新增或修改了重要要求；
- 发现了新的约束；
- 当前任务状态发生明显变化；
- 准备进行大规模重构；
- 准备结束当前一轮工作；
- 你判断当前上下文可能即将被压缩、裁剪或总结；
- 任何“如果以后忘记，会导致重复工作或错误决策”的信息出现时。

不要等到上下文真的快满了才第一次整理。

---

## 3. 上下文压缩前的强制操作

如果你发现当前上下文已经很长，或者系统可能即将进行 context compaction / context optimization / summarization：

**在继续大量工作之前，优先更新 `PROJECT_CONTEXT.md`。**

重点检查是否已经保存：

- 当前目标；
- 当前实现状态；
- 最近做了什么；
- 为什么这样做；
- 哪些方案已经尝试过；
- 哪些方案失败，以及失败原因；
- 尚未解决的问题；
- 下一步应该做什么；
- 用户明确要求；
- 不能违反的约束；
- 重要文件和代码位置；
- 实验结果和性能数据；
- 当前假设及其证据；
- 容易被上下文摘要遗漏的细节。

目标是：

> 即使当前聊天上下文立即全部消失，一个新的 Agent 只读取 `PROJECT_CONTEXT.md`、当前代码仓库和用户最新消息，也能基本无缝继续工作。

---

## 4. 文档不是聊天记录

不要机械记录所有对话。

`PROJECT_CONTEXT.md` 应保存的是**高信息密度、会影响未来工作的状态信息**。

应该保存：

- 事实；
- 约束；
- 决策；
- 决策原因；
- 当前状态；
- 用户偏好和明确要求；
- 已验证结论；
- 失败尝试；
- 尚未验证的假设；
- 重要数据；
- 文件位置；
- 下一步工作。

通常不需要保存：

- 寒暄；
- 已经完全失效且没有参考价值的中间讨论；
- 可以直接从代码中毫无歧义重新得到的琐碎内容；
- Agent 的冗长思考过程；
- 重复信息；
- 对未来没有任何影响的细枝末节。

原则：

> 保存“未来做正确决策所需的信息”，而不是保存完整聊天。

---

## 5. 必须区分事实、推断和计划

不要把猜测写成事实。

使用类似下面的表达：

- **已确认：** 已通过测试/代码/用户信息验证。
- **当前判断：** 根据现有证据推断，但尚未完全验证。
- **待验证：** 当前存在的重要假设。
- **计划：** 尚未执行的下一步。
- **已否定：** 已尝试并证明不可行的方案。

尤其是调试任务中，必须保存：

> “我们已经排除了什么，以及依据是什么。”

避免以后因为上下文丢失重新尝试同一个错误方向。

---

## 6. 保留“为什么”

不要只写：

> 使用方案 B。

应该尽量写成：

> 使用方案 B，因为方案 A 在 XXX 条件下导致 II=4，而方案 B 可以消除该 loop-carried dependency。除非 XXX 条件发生变化，否则不要恢复方案 A。

重要决策至少保存：

**Decision + Reason + Evidence/Result**

这样未来 Agent 不会在失去原始上下文后随意推翻已经验证过的决策。

---

## 7. 推荐的 PROJECT_CONTEXT.md 结构

维护以下结构，并根据项目需要扩展：

# Project Context

## 1. Mission

描述整个任务最终想实现什么。

包括：

- 最终目标
- 成功标准
- 用户最关心的指标

---

## 2. Hard Constraints

记录不能违反的约束，例如：

- 技术栈
- 硬件限制
- API / 接口要求
- 性能目标
- 兼容性
- 禁止修改的部分
- 用户明确要求

---

## 3. User Requirements

记录用户明确提出、且未来仍然有效的重要要求。

如果要求发生变化：

- 更新当前要求；
- 必要时在 Decision Log 中记录变化原因。

---

## 4. Current State

这是最重要的部分之一。

准确描述**现在项目处于什么状态**：

- 已完成什么
- 正在做什么
- 当前代码实现方式
- 当前能够运行到哪里
- 当前主要问题
- 当前性能/测试结果
- 当前工作分支或重要环境信息

这一部分必须保持最新。

---

## 5. Architecture / Mental Model

记录理解项目必须知道的结构：

- 模块关系
- 数据流
- 控制流
- 关键算法
- 重要接口
- 关键数据结构

避免保存可以直接从代码一眼看出的琐碎细节，重点保存“理解代码需要的模型”。

---

## 6. Important Files

记录重要文件：

| File | Purpose | Important Notes |
|---|---|---|
| `path/to/file` | 作用 | 为什么重要 |

如果有关键函数，也可以记录：

`file.cpp::function_name`

不要依赖模糊描述，例如“之前那个 kernel”。

---

## 7. Decisions

记录仍然影响当前实现的重要决策。

格式：

### D001 — 决策标题

**Decision:**  
最终决定。

**Reason:**  
为什么。

**Evidence:**  
实验、代码、benchmark 或用户要求。

**Implication:**  
这个决定对后续工作的影响。

**Status:** Active / Superseded

如果决策已经被替代，不要直接删除历史决策，将其标记：

`Superseded by D00X`

---

## 8. Experiments / Results

记录真正影响判断的实验。

格式：

### E001 — 实验名称

**Purpose:**  
验证什么。

**Setup:**  
关键配置。

**Result:**  
结果。

**Conclusion:**  
说明了什么。

不要保存大量无意义原始日志，只保存关键结果；必要时记录日志文件路径。

---

## 9. Failed Attempts / Things Not To Repeat

这是长任务中非常重要的一部分。

记录：

### F001 — 尝试

**Tried:**  
做了什么。

**Result:**  
发生了什么。

**Why it failed:**  
目前确认或推测的原因。

**Retry only if:**  
什么条件变化以后才值得重新尝试。

不要因为上下文被压缩就重复已经证明无效的尝试。

---

## 10. Bugs / Open Problems

记录仍未解决的问题：

### P001 — 问题名称

**Symptoms:**  
现象。

**Known facts:**  
已知事实。

**Ruled out:**  
已经排除的原因。

**Hypotheses:**  
当前假设。

**Next investigation:**  
下一步如何验证。

---

## 11. Current Working Set

这一部分只记录**当前最相关的工作上下文**，保持短小。

例如：

- 当前正在修改：`xxx.cpp`
- 当前关注函数：`foo()`
- 当前问题：pipeline II=4
- 当前假设：dependency 来自 xxx
- 当前准备验证：xxx

随着工作推进不断替换这里，而不是无限追加。

它应该让重新进入任务的 Agent 在几十秒内知道：

> “现在具体在干什么？”

---

## 12. Next Actions

维护按优先级排序的下一步。

例如：

- [ ] 验证 XXX
- [ ] 修改 XXX
- [ ] 跑 synthesis
- [ ] 比较 latency / II
- [ ] 如果结果为 XXX，则尝试 YYY

完成后及时删除、勾选或移动。

不要让这里积累大量已经失效的 TODO。

---

## 13. Validation Status

说明当前哪些东西已经验证：

- [x] Functional simulation
- [x] Unit tests
- [ ] C synthesis
- [ ] Co-simulation
- [ ] Implementation
- [ ] Hardware validation

根据具体项目调整。

---

## 14. Environment

只记录未来复现工作需要的环境信息，例如：

- OS
- compiler/tool version
- FPGA target
- Python version
- important dependencies
- commands
- branch
- important environment variables

不要记录密码、token、private key 等敏感信息。

---

## 15. Context Handoff Summary

这是给“未来失去聊天上下文的自己”看的。

控制在相对短的篇幅。

至少回答：

1. 我们在做什么？
2. 为什么这样做？
3. 当前做到哪里？
4. 最大问题是什么？
5. 已经排除了什么？
6. 接下来第一件事应该做什么？

每当任务状态发生重大变化时更新这一节。

---

## 16. Decision / Progress Log

只记录具有长期价值的关键变化。

使用：

`YYYY-MM-DD HH:MM — 内容`

例如：

`2026-09-10 20:30 — 将 softmax exp 实现从直接浮点 exp 改为 LUT + interpolation，原因是原实现 DSP/latency 较高。尚未完成 synthesis 验证。`

不要把这里变成逐分钟流水账。

---

# 8. 更新文档时的原则

每次更新时：

1. 先读取现有内容；
2. 修改已有状态，而不是简单在文件末尾不断追加；
3. 删除已经失效的“当前状态”；
4. 保留仍然具有历史价值的 Decision / Failed Attempt；
5. 合并重复内容；
6. 修正已经被新证据推翻的信息；
7. 保持 `Current State`、`Current Working Set` 和 `Next Actions` 最新；
8. 确保新的 Agent 可以直接接管。

文档应该随着任务增长而增长，但不能无限膨胀。

---

# 9. 控制文档自身长度

这个文档本身也可能变得很长，因此采用两种信息：

### Active Context

当前仍然影响工作的内容。

主要存在于：

- Current State
- Current Working Set
- Open Problems
- Next Actions
- Active Decisions

这一部分必须精炼、最新。

### Historical Context

过去但仍有参考意义的信息。

主要存在于：

- Decisions
- Experiments
- Failed Attempts
- Progress Log

当历史信息非常多时：

- 合并重复实验；
- 压缩已经完全解决的问题；
- 保留结论和关键证据；
- 删除不影响未来工作的中间过程。

优先保证：

> Active Context 短而准确，Historical Context 足够防止重复犯错。

---

# 10. 不要过度依赖该文件

`PROJECT_CONTEXT.md` 是长期记忆，不是对实际项目状态的替代。

恢复工作时，同时检查：

1. `PROJECT_CONTEXT.md`
2. 当前用户指令
3. 当前代码
4. git diff / git status / git log（如果适用）
5. 最新测试、编译或实验结果

如果它们不一致，重新验证事实并更新文档。

---

# 11. Git 项目的额外要求

如果当前任务位于 Git 仓库中，在合适的时候记录：

- 当前 branch
- relevant commit
- uncommitted modifications
- 当前修改过的重要文件

但不要把完整 diff 复制到 `PROJECT_CONTEXT.md`。

代码细节应该由 Git 保存。

`PROJECT_CONTEXT.md` 保存的是：

> 为什么改、现在改到哪里、结果如何、下一步是什么。

而 Git 保存：

> 具体改了哪些代码。

二者职责不要混淆。

---

# 12. 上下文恢复协议

如果你发现：

- 当前聊天明显缺失了早期上下文；
- 对之前为什么做某个修改没有印象；
- 用户说“之前我们已经试过了”；
- 当前代码出现无法从现有上下文解释的设计；

不要立即重新推导或重新实现。

先：

1. 阅读 `PROJECT_CONTEXT.md`；
2. 查看相关代码；
3. 查看必要的 Git history / diff；
4. 重建当前任务状态；
5. 再继续。

---

# 13. 最终原则

始终假设：

> “当前上下文可能在下一轮之后消失。”

因此，把真正重要的信息及时外部化。

但同时遵守：

> “不是保存更多信息，而是保存正确的信息。”

`PROJECT_CONTEXT.md` 的目标不是成为完整日志，而是成为一个可以让未来 Agent **无缝恢复任务状态、理解过去决策、避免重复试错、继续下一步工作**的可靠外部记忆。

在整个任务期间，主动维护该文件属于任务本身的一部分，而不是可选工作。
