# 任务：为 B 题解决方案仓库建立协作规范、文档体系与测试体系（Q1/Q2 优先）

## 背景与目标
三人团队 + AI 协作开发 B 题（无线电干扰源定位与清除），Python 技术栈。
当前痛点：成员之间工作不同步、代码正确性不可见、哪些结果可信不清楚、
新成员拉取仓库后无法了解进度。

本任务建立"代码组织 + 文档体系 + 测试体系"三位一体的仓库规范，
并把规范固化到 AGENTS.md，使后续所有 AI 会话自动遵守。

## 权限边界（最高优先级，违反即任务失败）
1. 【禁止一切 git 操作】不得执行 git add/commit/push/branch/mv/checkout 等任何
   git 命令；版本管理由人工负责。移动文件使用普通 mv/cp。
2. 【状态标记权归人工】你不得将任何题目标记为【已验证】或【模拟器未测试】。
   你的职责是产出《验证步骤清单》（见第五步），由人工执行验证后自行更新状态。
   当前四题的初始状态一律标注为【待验证】。
3. 【接口以现有代码为准】API.md 从扫描到的真实函数签名归纳，不得凭空设计；
   归纳过程中遇到任何无法确定的语义（参数单位、返回值含义、调用时序），
   立即停止该部分工作，整理成问题清单向我询问，得到答复后再继续。

## 第一步：现状扫描（必须最先完成，完成后暂停等待人工确认）
1. 递归列出 solution/ 下所有源文件
2. 对每个文件列出：文件路径、所有函数/类签名（含参数类型与返回类型）、
   每个函数的一句话功能描述（从代码逻辑归纳，禁止编造）
3. 按以下四类初步归类并输出清单：
   - 属于 Q1 / Q2 / Q3 / Q4 的实现
   - 被多题复用的公用逻辑
   - 疑似已废弃的旧文件（无引用、功能被替代）
   - 归类不明确、需人工判断的
4. 汇总你发现的"无法确定的接口语义"问题清单，一并向我提问
5. 输出《现状扫描报告》，**在我确认归类结果之前，不得移动任何文件**

## 第二步：目录重组（基于扫描报告的人工确认结果执行）
目标结构：
solution/
├── src/
│   ├── q1/  q2/  q3/  q4/        # 各题算法实现，可互相 import
│   ├── common/                    # 公用函数（几何工具、IO、常量等）
│   └── legacy/                    # 确认废弃的旧文件移入此处
├── tests/
│   ├── q1/  q2/  q3/  q4/        # 各题 testbench
│   │   ├── data/                  # 测试数据文件（生成器产出、对拍器读取）
│   │   └── test_res.md            # 该题最近一次人工验收记录
├── 快速上手指南.md
└── TODO.md
（API.md 放在各题 src/qN/ 目录下，见第三步）

重组规则：
- 移动文件时同步修复所有 import 路径，重组后运行已有入口确认无破坏
- legacy/ 中每个文件同目录放置 <文件名>.README.md，三行说明：
  原功能、为何废弃、被哪个新文件替代
- Q3/Q4：只做代码归位到 src/q3、src/q4，不建测试（对拍策略未定）

## 第三步：API.md（Q1/Q2 各一份，放 solution/src/qN/API.md）
用途：作为测试数据与对拍程序的接口契约。AI 据此生成测试数据，人工据此理解模块边界。
基于扫描到的真实函数签名归纳，遇到不确定语义立即暂停询问。内容：
1. 该题对外暴露的核心函数清单：函数签名、参数含义与单位、返回值含义
2. 输入数据规范格式（JSON schema + 字段表）：
   每个字段名称、类型、单位、取值范围、物理含义；
   一个最小合法输入示例 + 一个边界输入示例
3. 输出数据规范格式：同上
4. 前置条件与不变量（如"示向度误差 ±1°"、"干扰源间最小距离"）
5. 与官方模拟器的边界：明确哪些数据来自模拟器、哪些由内部生成；
   【模拟器协议细节当前未知，一律标注"协议待补充"占位】

## 第四步：README.md（Q1/Q2 各一份，放 solution/src/qN/README.md；
Q3/Q4 各放一份占位 README，仅写题意复述与"策略未定、待对拍方案确定后补全"）
目标读者：不了解该题实现的本科队友，通俗易懂，禁止堆砌术语。结构：
1. 该题问的是什么（两三句话复述题意）
2. 算法思路（文字版流程图或步骤列表）
3. 算法 ↔ 代码对应表（核心）：
   | 算法步骤 / 数学公式 | 对应函数（文件:函数名） | 说明 |
4. 输入输出示例（引用 API.md）
5. 当前实现状态与已知局限（诚实标注，不夸大）

## 第五步：测试体系（仅 Q1/Q2，放 solution/tests/qN/）
每题三类，分开写、分开跑：
1. test_unit.py —— 独立分块测试：对核心子函数（射线求交、旋转卡壳、
   时间记账等）用手算已知答案的样例逐个断言，失败时输出诊断信息
2. test_duipai.py —— 对拍程序（Q1/Q2 是几何计算，有唯一正确答案）：
   实现一份独立的暴力参考实现（如直径用 O(n²) 双重循环对拍旋转卡壳 O(n)），
   在随机数据上逐点比对，不一致时打印两个实现的输出与输入数据
3. gen_data.py —— 数据生成器：按 API.md 的输入规范生成 JSON 测试数据
   写入 data/；三种模式：--mode random / boundary / adversarial
   （随机 / 极端参数 / 针对已知易错点构造），附带 --seed 保证可复现
4. verify_manual.md —— 【人工验证步骤清单，状态判定的唯一依据】：
   列出人工验证该题所需的全部操作：跑哪些脚本、期望看到什么输出、
   哪些数字可以手算交叉核对（给出手算过程）、验证通过后应将状态改为【已验证】、
   验证失败应如何记录。人工按此清单执行后自行更新状态，你不得代劳。
运行方式与依赖写入各题 README；样例命令：
  python tests/q1/gen_data.py --mode random --seed 42
  python tests/q1/test_unit.py
  python tests/q1/test_duipai.py

## 第六步：全局文档
1. solution/快速上手指南.md：
   - 仓库结构说明（一段话 + 目录树）
   - 四题状态总表（核心，人工维护，你只建表并填初始值）：
     | 题号 | 状态 | 最近更新 | 负责人 | 一句话说明 |
     状态取值与判定标准：
     · 【未开始】无代码
     · 【待验证】代码写完、本地跑通，但未经人工按 verify_manual.md 验证
     · 【已验证】人工按清单执行验证通过后，由人工标记
     · 【模拟器未测试】本地已验证且在官方模拟器实测前，由人工标记
     当前四题初始状态一律填【待验证】（Q3/Q4 视扫描结果，若代码不完整填【待验证】并注明）
   - 三分钟上手流程（clone → 装依赖 → 跑哪个脚本 → 看哪个文件）
2. solution/tests/qN/test_res.md（Q1/Q2 建立模板）：
   模板字段：日期、执行人、跑的测试、结果（通过/失败/指标数字）、
   发现的问题、状态是否变更。首行预填当前状态【待验证】，
   注明"此文件由执行验证的人工填写"。
3. solution/TODO.md：维护"正在探讨但未实施"的方案，
   每条含：方案描述、提出人、当前讨论结论、转化为实施的触发条件；
   预填两条：Q3/Q4 对拍策略待定、模拟器协议对接方案待补充
4. AGENTS.md（仓库根目录）：将上述全部规范浓缩为未来 AI 会话自动遵守的清单，
   至少包含：
   - 目录结构约定与各文档的职责
   - 修改代码后必须同步更新的文档清单（README 对应表 / API.md / 状态表）
   - API.md 是接口契约，变更须人工确认
   - 状态标记判定标准（并明确：AI 不得标记【已验证】/【模拟器未测试】）
   - 【禁止 AI 执行任何 git 操作】
   - 遇到接口语义不确定时：停止、整理问题、询问人工
