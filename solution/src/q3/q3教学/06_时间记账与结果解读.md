## 1. 虚拟时间的"价格表"（`common/time_model.py`）

官方对每一种机器人动作都定了统一的计时规则。策略**每一秒都要省**，所以必须先会算账。
看 `common/time_model.py`：

```python
def measure_cost(previous, target, current_channel, target_channel):
    return TimeBreakdown(
        movement_s  = math.dist(previous, target) / 5.0,          # 移动：距离÷5 m/s
        switching_s = 0.0 if current_channel == target_channel else 1.0,  # 换频
        measurement_s = 5.0,                                       # 固定测一次 5s
    )

def clear_cost(previous, target, success):
    return TimeBreakdown(
        movement_s = math.dist(previous, target) / 5.0,            # 移动
        optical_s  = 3.0,                                         # 光学扫描 3s
        laser_s    = 2.0 if success else 0.0,                     # 命中后激光 2s
    )
```

| 开销项 | 规则 | 何时加入 |
|---|---|---|
| 移动 | 移动距离 ÷ 5 m/s | 每次 measure / clear 都会移动 |
| 切换频道 | 换频道 +1 s，不换 0 s | measure 且切到别的频道 |
| 测量 | 固定 +5 s | 每次 measure |
| 光学 | +3 s | 每次 clear |
| 激光 | 成功 +2 s | clear 且命中 |

`TimeBreakdown.total_s` 就是这五项的和。每次动作花掉多少，`FakeSimulator`
都累加进 `virtual_time`。

> 直观记：**测一次至少 5 秒；移动一公里 200 秒；clear 成功一共 3+2=5 秒**。
> 所以"多测没用的点"是最大的时间浪费，其次是大距离移动——策略扫描和细化都在权衡这两者。

## 2. 为什么 demo 花了 2959.6 秒？（把账算给你看）

demo 最终 `virtual_time_s ≈ 2959.6`。这笔账怎么来的？我们用动作结构粗算一遍。

**宏观结构**（来自真实输出）：

```
measure ×137 + clear ×1，外加 enter/exit 各 1（不计时）
```

**① 扫描阶段 7 个覆盖点**：机器从原点出发，要在这 7 个点之间移动。
`ring7` 的 7 点坐标（第 03 篇表）里，相邻大点相距可观（如 (0,0)→(1500,0) 是 1500m）。
7 个点走一圈，粗估移动在 6000~7000m → 移动时间约 1200~1400 秒。
（【考古注 2026-09-12】此处 6000~7000 是**移动路程的米数**，与"总虚拟时间约
6000s"的说法无关；可用于对照的数字：ring7 扫描总虚拟 2633s（移动 1800 + 检测
700 + 切换 133），pure_ring8 为 2172.7s——见 `docs/性能演进考古_20260912.md`。）

**② 每个 point 测 20 个频道**：7 点 × 20 频道 ≈ 140 次 measure。按 `measurement_s=5`，
光"测"就是 140 × 5 = **700 秒**。

**③ 切换频道**：每个覆盖点内从频道 1 换到 20，跨频道要 +1s，约 20 次/点 × 6 点 ≈
一百多次切换 → 约 **130~200 秒**。

**④ 频道 3 的 3 次 direction + 细化移动**：3 次额外测量 + 移动去 (777,-35) 的方向，
加若干百秒。

**⑤ 最后的 clear**：位置 (1500,0)→(1196,96) 移动约 300m=60s，加 3+2=5s。

把 ①~⑤ 相加，量级 **≈2900~3000 秒**，与实测 2959.6 秒吻合。这验证了：**策略的时间
几乎全部耗在"扫描移动 + 扫 20 频道 + 频道切换"上**，清除本身只占约 5 秒。

> 你可以打开 `teach_demo.json`，随便挑几条动作看 `virtual_time_s` 的增长，自己加一加，
> 就能体会每一步到底花在哪。这正是"理解结果含义"的最好练习。

## 3. demo 输出 JSON：从上到下逐字段读

跑完 `cli.py` 会写出一个 `RunSummary.as_dict()` 序列化的 JSON，顶层字段如下
（带实际 demo 数值）：

```jsonc
{
  "actions": [...],            // 一张表：每一步发生了什么，见第 4 节
  "cleared_channels": [3],          // 清掉的频道：只有频道 3
  "absent_channels": [1,2,4,...,20], // 判无源的频道：其余 19 个
  "virtual_time_s": 2959.61,        // 全部动作累计花掉的虚拟时间(秒)
  "exit_reason": "user_exit"        // 怎么结束的：正常主动退出
}
```

- **`cleared_channels`**：这台机器"消灭"了多少真实源（本 demo 就 1 个）。
  **看得分时最核心的指标**——清掉越多、越正确，越好。
- **`absent_channels`**：被判定"无源"的频道。
- **两者并起来**：一共正好 20 个频道，一个不漏 = "终端证书完整"（第 05 篇）。
- **`virtual_time_s`**：总时长。**正式规则是墙钟 20 分钟上限**（demo 用的 360000 秒是
  本地模拟的宽松值，不做真实参考，见 07 篇），所以实战里这个数必须压在限制内。
- **`exit_reason`**：`user_exit` 表示是我们主动选择退出、圆满收场
  （若超时/被拒则是其它值）。

## 4. `actions` 数组：每一步的完整记录

`actions` 是"日志"，每一条都是 `{action, response}` 一对：

```jsonc
{
  "action": {
    "kind": "measure",            // 动作类型
    "request_id": "measure-25",   // 唯一 ID
    "position": {"x": 1500.0, "y": 0.0},   // 动作位置(仅measure/clear有)
    "channel": 3                  // 频道(仅measure/clear有)
  },
  "response": {
    "accepted": true,
    "virtual_time_s": 442.0,        // 做完这步后的累计时间
    "measure_result": "direction",  // 本次测量结果
    "svd_deg": 162.46               // direction 时带的方向角
  }
}
```

读懂这条你就能手动"复盘"整个 demo：

- `kind` → 这步在干嘛；
- `position`/`channel` → 去了哪、测哪个频道；
- `virtual_time_s` → 累计时间，**看它增长可追踪时间**；
- `measure_result` → no_signal / direction / near；
- `svd_deg` → direction 的示向度（±1° 误差），是定位的原材料。

> **清理思路**：如果你要写论文，把 `actions` 里所有 `measure_result=="direction"` 的
> 行挑出来排时间序，就是该频道的"观测历史"——第 05 篇已经示范过频道 3 的三条。

## 5. 三个"离官方成绩"的提醒（结果的边界）

`cli.py` 结尾自己打印了一行：

```python
print("这是本地规则模拟，不是官方测试。")
```

这句话是**诚实条约**，务必记住：

1. **demo 的 2959.6 秒、140 动作只是本地模拟**：它用一个 `FakeSimulator` 按"人工定的
   规则"模拟，不是官方模拟器，也不是正式成绩。
2. **demo 只有一个源**：真实案例有 10~16 个源、20 个频道可能多个有源，复杂得多。
   这个 demo 只证明"最基本的全向源流程能跑通、能收尾"。
3. **正式限制是 20 分钟墙钟**：在线时受 `max_real_duration_s=1200`（即 20 分钟）约束，
   demo 的宽松 360000 秒不代表实战预算。所以"清得快不快"在实战中远比"能不能清掉"更重要。

**结论**：demo 输出证明了**算法逻辑正确、能跑到自然退出**；但论文里的性能指标
（清除率、平均清除时间）必须来自官方模拟器多案例的正式结果，不能用这份 demo 数字。
