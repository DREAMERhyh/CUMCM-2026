# Q3 零基础教学（02）：策略状态机 + 机器人主循环

这一篇把整套系统的"骨架"讲清楚：**机器人怎么一刻不停地把动作做下去**。
读完后你应该能回答：一条动作从"策略想到它"到"机器人执行完、把结果反馈给策略"，
中间到底发生了什么。

---

## 1. 两个主角：策略（大脑）和客户端（身体）

整个离线系统由两部分组成，两者在一个主循环里不断对话：

```
┌────────────┐    "我下一步该做什么？"    ┌────────────┐
│   策略     │  ──────────────────────>  │  客户端    │
│ (Q3Policy) │   next_action(state)      │ (FakeSim.) │
│            │  <──────────────────────  │            │
│            │   "做这个：measure(...)"  │  执行动作   │
│            │  ──────────────────────>  │            │
│            │   apply_response(...)     │  算出结果   │
│            │  <──────────────────────  │            │
│            │   "结果：direction 162°"  │  返回响应   │
└────────────┘                           └────────────┘
```

- **策略 `Q3Policy`**：我们的"大脑"，负责决策——记住当前状态、决定下一个动作。
- **客户端 `sim.fake.FakeSimulator`**：模拟"赛场与机器人身体"，按物理规则执行动作、
  返回结果。（正式版本会换成 `runtime/http_client.py` 连官方模拟器，接口相同。）

这个"一问一答"的循环就是主循环，下一个动作由**当前状态 + 上次结果**共同决定——这就是
**状态机**。

---

## 2. 状态：策略"记住"了什么？

策略不能只靠一拍脑袋做动作，它要记住一路上发现的一切。这些记忆全部放在
`Q3State` 这个数据类里（`policy.py`）。挑几个最重要的字段看：

```python
@dataclass
class Q3State:
    phase: str              # 当前处于哪个阶段："scan" / "resolve" / "exit"
    position                # 机器现在在哪
    current_channel         # 机器当前切在哪个频道
    virtual_time_s          # 已经花掉的虚拟时间
    cleared: set[int]       # 已确认清除的频道集合
    absent: set[int]        # 已确认无源的频道集合
    sources: dict           # 频道 -> 该频道的"跟踪档案 SourceTrack"
    forced_clear            # 当测量返回 near 时，强制去清除的位置
    ...
```

其中最核心的是 `phase`——它决定了策略此刻**该干什么**。我们叫它"策略的四个阶段"。

---

## 3. 四个阶段（phase）：整个策略的骨架

策略永远处于下面四种阶段之一，做完一件事就切换：

```
   [enter 入场]
        │
        ▼
   [scan 扫描] ──所有频道都有了归宿──> [resolve 决议] ──全部搞定──> [exit 退出]
        └────────────────────────────────────────────────────────────────┬──► 结束
```

| 阶段 | phase 取值 | 干什么 | 什么时候结束 |
|---|---|---|---|
| 入场 | （未 enter） | 先发一个 `enter`，拿时间上限 | `enter` 被接受后 |
| 扫描 | `"scan"` | 在 7 个覆盖点上，把 20 个频道挨个测一遍，找"谁有信号" | 所有覆盖点都扫完 |
| 决议 | `"resolve"` | 对"测到过 direction 的频道"逐个定位、细化、清除 | 所有 source 频道被清除 |
| 退出 | `"exit"` | 发 `exit` 结束比赛 | 返回最终 summary |

> 注意：demo 里绝大多数动作（137 个 measure 里的绝大多数）都发生在 **scan** 阶段。
> 只有在 scan 阶段"确认某频道有源"后，才进入 resolve 去处理它，最后 exit。
> （严格说 resolve 在 demo 里只有一次——因为只有一个真实源频道 3。）

## 4. 主循环：动作怎么被"喂"给机器人

主循环在 `runtime/runner.py` 的 `run_policy()` 里，逻辑非常直白——一个 `for` 循环：

```python
for _ in range(max_actions):          # 最多做 max_actions 次动作（防死循环）
    action = policy.next_action(state)       # ① 策略说：下一步做这个动作
    response = client.execute(action)        # ② 客户端：执行并返回结果
    policy.apply_response(state, action, response)  # ③ 策略：把结果记进状态
    # ④ 若刚执行完 exit 且被接受 → 比赛结束
    #   导出 RunSummary 并 return
```

四个步骤各有什么讲究，我们逐一看。

### 第 ① 步：`next_action(state)`——策略"想出"下一个动作

策略类里的方法。注意它开头有一个小细节：

```python
def next_action(self, state):
    if state.pending is not None:      # 如果上一个动作还没落实，就原样返回它
        return state.pending
    ...
```

为什么要这样？因为**有些动作（measure/clear）含定位、决策需要时间**。策略一旦把某个
动作"想出来"，就会把它暂存到 `state.pending`，下一次 `next_action` 直接返回同样的
动作，直到 `apply_response` 确认它被执行完、把 `pending` 清空为止。这保证了：
**策略不会在上一个 action 的结果回来前，又凭空编出第二个动作**。

### 第 ② 步：`client.execute(action)`——机器人真的去做

`FakeSimulator.execute()` 会：校验收到的动作合法、判断是否之前做过（幂等缓存）、
然后按动作类型算时间、移动、测量/清除、返回 `response`。

### 第 ③ 步：`apply_response(state, action, response)`——策略消化结果

这是策略"学习"的地方。`apply_response` 会：

1. 核对 `response` 对应的正是 `state.pending` 那个动作；
2. 用返回值更新 `virtual_time_s`；
3. 按动作类型处理结果：
   - `enter` → 记录"已入场"；
   - `measure` → 更新机器位置/频道，把测量结果写进对应频道的 `SourceTrack`；
   - `clear` → 根据成功与否，把频道划入 `cleared` 或标记"证书失败"；
   - `exit` → 标记已退出。

**关键**：`apply_response` 只负责"记账"，不决定下一步动作——决定权始终握在
`next_action` 手里。这就是"一问一答"循环能稳定推进的原因。

## 5. 一条动作的完整旅程（用 demo 的第一条动作示范）

拿 demo 的第一条动作 `enter` 举例，感受一下信息流：

```
① next_action：state 还没 entered → 返回 Action("enter","enter-1")
② FakeSimulator.execute：校验 → enter 合法 → 返回 accepted=True
                        + max_virtual_duration_s=360000 等
③ apply_response：accepted=True → state.entered=True，把 pending 清掉
④ 不是 exit 动作 → 循环继续
```

再看 demo 里第 24 个动作（第一次测到源方向的 `measure`）：

```
① next_action：处于 scan 阶段，选中覆盖点 (1500,0)、频道 3
② execute：机器人移动到 (1500,0)（计移动时间），
           切到频道 3（计切换时间+测量时间），返回
           measure_result="direction", svd_deg=162.46
③ apply_response：更新 position 与 current_channel=3，
           在 sources[3] 里记下这条观测 (位置, 示向 162.46°)，
           并据此长出一个"嫌疑区域"（第 04 篇主角）
```

从此，策略"知道"频道 3 有一个源，大致在 (1500,0) 的南偏西方向。

## 6. 外层：谁调用了主循环？

`cli.py` 负责"组装"，把策略和客户端像插槽一样插进主循环：

```python
client  = FakeSimulator([FakeSource(3, (1200,100), 1000)])   # 造出"赛场"
policy  = Q3Policy(max_refinements=2, fim_cpu_time_limit_s=6)  # 造出"大脑"
summary = run_policy(policy, client, max_actions=args.max_actions) # 跑主循环
```

跑完得到一个 `RunSummary`，里面有动作清单、清除列表、absent 列表、虚拟时间和退出原因——
这正是 demo 输出 JSON 的内容（第 06 篇逐字段解读）。

> 你在 `cli.py` 里看到的 `--max-refinements 2` 和 `--fim-cpu-time-limit-s 6` 是策略的
> 两个"超参数"：前者限制每个频道最多细化两次，后者限制单次 FIM 真实计算不超过 6 s。
> 后面的细化篇会详细讲它们的作用。
