## 1. 怎么把测试跑起来？

在 `solution/` 目录执行（Windows PowerShell）：

```powershell
python -B -m unittest discover -s tests/q3 -p 'test_offline.py' -v
```

期望输出以 `OK` 结尾（7 项测试全过）。`-B` 是不写 `__pycache__`，`-v` 显示每个测试名。

> 若想看采纳率统计，`-v` 给出的就是每个测试的 pass/fail。全部 OK 代表这一层验证通过，
> 但**这不代表官方通过**（如 00 篇所说，需后续连官方模拟器）。

## 2. 七个测试逐一讲：它们在保护什么？

测试文件是 `tests/q3/test_offline.py`，测试类叫 `Q3TheoryTestbench`。我们按顺序看。

### 测试 1：`test_refinement_consumes_q2_hybrid_recommendation`

```python
with patch("q3.policy.plan_measurement", return_value=fake_plan) as planner:
    self.assertEqual(policy._refinement_point(state, track), (80.0, 90.0))
```

**它验证的是**：Q3 的细化点确实取自 `plan_measurement` 返回的 `selected_point`；
并且 Q2 的配置正确带上了 `continuous_fim_enabled=True`、`fim_cpu_time_limit_s=6.0`、
`near_optimal_region_mode="off"`。
**保护点**：细化委托关系不会被改丢；Q2 超参数与线上默认保持一致。
（用 `patch` 假造了 Q2 返回，只测 Q3 的取用逻辑，不让测试真的跑 Q2 全流程。）

### 测试 2：`test_ring7_covers_random_target_disk_at_radius_1000`

```python
center = ring7()
for _ in range(5000):
    radius = 1800*sqrt(random())        # 半径 1800 内随机撒"可能源"
    ...最近距离...
self.assertLessEqual(worst, 1000.0)
```

**验证**：在半径 1800（赛场大小）内随机撒 5000 个点当"可能源"，它们到 7 个覆盖点里
最近一个的距离**最大不超过 1000 m**。
**保护点**：`ring7` 的覆盖确实充分——任一源都落在某个覆盖点 1000m 内，比最大接收半径
1500m 小很多，留足余量。这支持了第 03 篇"测不到=无源"的结论。

### 测试 3：`test_strip_clear_grid_covers_full_bearing_rectangle`

```python
points = list(strip_clear_points((0,0), 0.0))
# 在覆盖矩形里按 10m × 13.16m 抽样
self.assertLess(worst, 20.0)
```

**验证**：保底清除网格（`strip_clear_points`）能覆盖"沿首测方向的矩形条带"——抽查点里
离最近网格点的最大距离 **< 20m**。
**保护点**：第 05 篇的保底清除确实"任何落带内的源，总有网格点离它 ≤20m"，从而保证
至少一个 clear 会成功。

### 测试 4：`test_official_199_second_accounting_example`

```python
actions = [...enter, measure(300,400)ch1, measure(300,400)ch2,
               clear(300,0)ch3, measure(300,400)ch2...]
self.assertAlmostEqual(response["virtual_time_s"], 199.0)
```

**验证**：用官方给出的**标准动作序列**复算，时间账必须正好是 **199 秒**。
**保护点**：`time_model` 的计时规则与官方算法完全一致。这是"一分一秒都要对上账"的
黄金用例——数字不对说明计时实现有偏差。

### 测试 5：`test_request_id_is_idempotent_in_fake_client`

```python
first = client.execute(action)
second = client.execute(action)
self.assertEqual(first, second)          # 同 ID 同动作，结果必相同
self.assertEqual(client.virtual_time, 105.0)  # 且不会重复计时间
```

**验证**：同一 `request_id` 的同一动作**重试不会重复推进时间**（幂等）。
**保护点**：网络重试安全——正式环境里若请求超时重发，不会把机器时间和状态搞乱。

### 测试 6：`test_official_payload_does_not_leak_internal_fields`

```python
payload = build_request_payload(action, "team")
self.assertEqual(set(payload), {"arena_id","robot_id","request_id","position","channel"})
self.assertNotIn("kind", payload)        # 内部字段不上传
```

**验证**：发给官方的 HTTP 请求负载里**只含 protocol 允许的字段**、没有泄露内部 `kind`。
**保护点**：网络边界不泄露内部实现，符合协议契约（`sim/protocol.py`）。

### 测试 7：`test_q3_policy_finitely_clears_and_certifies_channels_offline`

```python
client = FakeSimulator([FakeSource(3, (1200,100), 1000)])  # 就一个全向源
policy = CountingQ3Policy()              # 数一下 refine 被调几次
summary = run_policy(policy, client, max_actions=1000)
self.assertEqual(summary.cleared_channels, [3])           # 清了频道 3
self.assertEqual(summary.absent_channels,[c for c in 1..20 if c!=3])  # 其余19无源
self.assertEqual(summary.exit_reason, "user_exit")         # 正常退出
self.assertLess(len(summary.actions), 1000)               # 有限动作内收尾
self.assertEqual(policy.refinement_plan_count, 2)         # 恰好细化2次
```

**验证**：在 `max_actions=1000` 的动作上限内，策略能**有限**地：清掉真实源频道 3、
判其余 19 频道无源、证齐证书、正常退出；且对频道 3 恰好做了 2 次细化。
**保护点**：这是**端到端主线测试**——整条 scan→resolve→clear→exit 流程必须收敛、
不卡死、不多做动、细化次数符合预期。**它就是我们全篇 demo 的自动化版。**

> 这 7 个测试共同构成一张"安全网"：计时、覆盖、保底、幂等、协议、收敛、细化委托。
> 哪一个挂了都说明某一环被改坏。**它们不测"性能有多好"，只测"正确性和不会崩"。**

## 3. 系统目前已知的局限（实话说在前头）

这是教学文档里最重要的诚实交代，写论文和答辩时要主动说、要能自圆其说。

### 局限 A：Q3 策略定位不清时，靠"网格硬清"兜底、效率有限

当细化次数用完、MEC 仍然过大时，`fallback_clear` 沿首测方向铺 228 个网格点逐个 clear。
这**保证能清掉、但很费时间**。对正式 10~16 源场景，若多个源都触发保底，时间会吃紧。
（演示单源案例没触发，不代表多源不会。）

### 局限 B：定位区域用"外切多边形"保守近似，区域偏大

圆一律用外切正多边形近似（宁大勿假），所以 MEC 半径可能比真实略大，
导致有时要多细化一次才敢 clear。**保守带来安全，也带来时间成本。**

### 局限 C：只验证了"全向源"

`FakeSource.direction_deg is None` 才是全向源。若官方场景含定向源（有朝角），
`_visible` 逻辑不同，当前策略未针对定向源优化。上线前需确认官方源类型。

### 局限 D：未连接官方模拟器、未测多源/真实网络

- 官方 HTTP、异常码、真实网络重试尚未验证；
- 10~16 源的官方随机案例没有跑过清除率平均；
- 3 次展示/正式测试的清除比例未知；
- 20 分钟墙钟约束和真实 RPC 吞吐未实测。

### 局限 E（数值/近似，继承自 Q2 的声明）

`q2/planner.py` 的 `limitations` 里写清了四条近似声明，Q3 细化同样继承：

1. 源物理圆形区域用外切正多边形近似；
2. 保证接收域是内近似、可能接收域是外近似；
3. 最坏情形只在有限边界场景上算，不声称连续全局最优；
4. 连续 FIM 优化的是信息量替代目标，最终用离散集合同口径比较。

以上每一条都不是"藏起来的 bug"，而是**刻意权衡**。答辩时能主动讲出 trade-off，
反而说明对算法理解到位。

## 5. 全系列小结

把这 8 篇串起来，就是 Q3 的完整图景：

- **01**：20 频道、三种测量结果、clear、虚拟时间的游戏规则；
- **02**：策略 = 四阶段状态机 + 主循环（问→做→记）；
- **03**：scan 阶段——7 个覆盖点 + 20 频道地毯式排查 → absent 判定；
- **04**：定位与细化——嫌疑区域、MEC、certified clear、调 Q2 推荐点；
- **05**：保底与收尾——网格硬清、证书失败切换、终端证书、exit；
- **06**：时间记账 + demo 逐字段读懂（140 动作 / 2959.6s / cleared、absent）；
- **07**：测试保护点 + 局限清单 + 上线检查。

**一句话总结整个 Q3**：
> "先用便宜的 scan 摸清 20 个频道谁有源、谁无源；对有源的频道靠多次测角交会、
> 必要时用 Q2 的信息量推荐点细化到 20 米内一击清除；实在不行就用方向网格保底硬清，
> 最后证齐 20 个频道的清/无后优雅退出。"
