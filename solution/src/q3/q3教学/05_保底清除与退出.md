# Q3 零基础教学（05）：保底清除与退出 —— "万一没定位准"和"怎么收尾"

前 04 篇讲得顺风顺水：扫描找到源 → 细化定位 → R≤20 致命一击。但现实不会总是这么理想。
这一篇回答三个"刁钻"问题：

1. 细化次数用完、MEC 还是 >20m，怎么办？（保底清除 fallback）
2. certified clear **失败了**怎么办？（证书失败）
3. 什么时候宣告"全部搞定"、怎么退出？

---

## 1. 先看 `_resolve_action` 的完整分支（把上一篇的碎片拼起来）

还记得上一篇我们只摘了"R≤19.9 就 clear"和"R>19.9 且没细化完就 refine"两段。
其实完整逻辑是四种情况层层递进，都在 `_resolve_action` 里：

```python
remaining = [频道 in sources，且还没清除的]          # 待处理的频道
if not remaining:                                    # ① 没有待处理频道了
    # 检查 cleared|absent 是否覆盖全部 20 个频道
    if state.cleared | state.absent != set(range(1,21)):
        raise RuntimeError("频道终止证书不完整。")
    state.phase = "exit"                             # 全部搞定 → 退出
    return None

track = state.sources[remaining[0]]
radius = track.region["minimum_enclosing_circle"]["radius"]

if radius <= 19.9 and not track.certificate_failed:  # ② 足够准 → 自信清除
    return self._action(state, "clear", 圆心, channel, "certified_clear")

if track.refinements < self.max_refinements:         # ③ 还不够准 + 还能细化 → 细化
    point = self._refinement_point(state, track)
    return self._action(state, "measure", point, channel, "refine")

# ④ 细化用完了，R 还是太大 → 进入保底通道
if not track.fallback_points:                        # 第一次时才生成保底点列
    first = track.observations[0]                     # 用第一次测角的信息
    track.fallback_points = list(strip_clear_points(first.position,
                                                    first.bearing_deg))
...
return self._action(state, "clear",
                    track.fallback_points[track.fallback_index],
                    channel, "fallback_clear")
```

四种情况对应四种动作：无源→exit、够准→clear、不足但可细化→measure、穷尽→保底 clear。
**策略永远有路可走，绝不卡死**——这是健壮性的核心。

## 2. 保底清除：细化用尽后的"倔强收尾"

**问题**：细化次数用完了，MEC 半径还是很大（>19.9），但源确实存在（我测到过 direction），
总不能不管它吧？

**保底思路**：我不知道源的**精确**位置，但我知道它**大致方向**（第一次 direction 给过
示向角）。于是沿着这个方向，把可能范围用**细密的网格**铺一遍，挨个 clear，总有一个点
离源能 ≤20m，从而清掉它。

网格来自 `strip_clear_points`（第 03 篇提过的 `coverage.py`），逻辑回顾：

```python
def strip_clear_points(sensor, bearing_deg):
    theta = radians(bearing_deg)          # 示向角 → 弧度
    u = (cosθ, sinθ)                       # 沿"偏离源"方向
    n = (-u[1], u[0])                      # 垂直方向
    for row, offset in enumerate((-20, 0, 20)):    # 三条平行带
        for index in ...:                           # 每条带沿线 76 步
            yield (sensor + 20*index*u + offset*n)  # 每 20 米一个点
```

它产出 `3 × 76 = 228` 个点：三条间距 20m 的平行带，每条沿源方向每 20m 一个探测点。
为什么间距都取 20m？因为 **clear 的成功判据就是"源距清除点 ≤20m"**——如果源落在这条
局部矩形带内，那么它到某个网格点的距离必然 ≤20m，至少一个 clear 能成。（测试验证：
在覆盖矩形里抽查，最大"离最近点距离"确实 <20m。）

`fallback_clear` 就是顺着这份点列，逐个点去 clear：

```python
if track.fallback_index >= len(track.fallback_points):
    raise RuntimeError("频道X有限清除保底耗尽。")   # 理论不该发生
return self._action(state, "clear",
                    track.fallback_points[track.fallback_index],
                    channel, "fallback_clear")
```

每失败一次，`fallback_index += 1`，换下一个点继续试——直到成功或点列穷尽。

> demo 里没用上保底：因为细化两次后 R 已经 ≤19.9，直接 certified_clear 成功了。
> 保底是"以防万一"的 safety net，实战里定位失败时兜底用的。

## 3. 保底 vs 自信清 which 失败后怎么区分处理？

策略给两种 clear 贴了不同标签，`apply_response` 里也区别对待：

| 模式 | 何时发起 | 若 clear 失败 |
|---|---|---|
| `certified_clear` | R≤19.9，"证明"了源在圆内 | 说明我的几何证明出错了！标记 `certificate_failed=True`，并把细化次数设为上限（不再细化），改走保底 |
| `fallback_clear` | 细化用尽，逐个网格点硬清 | 网格点 +1，继续试下一个 |
| `near_clear` | 测到 near 后强制清 | 理论不该失败，失败直接报错 |

看 `apply_response`：

```python
if mode == "certified_clear":
    track.certificate_failed = True               # 证明失败，承认
    track.refinements = self.max_refinements      # 关掉细化，直接保底
elif mode == "fallback_clear":
    track.fallback_index += 1                     # 下个网格点
```

**"certified clear 失败"意味着**：我觉得源在圆心 20m 内，但实际不在——要么是测角误差越了界，
要么数值有问题。这时必须**收拢策略**：不再幻想靠精确定位，直接把该频道的细化次数清零，
转保底网格硬清。这就是为什么 `_resolve_action` 第一个分支要判断
`and not track.certificate_failed`（一旦证书失败，即使 R≤19.9 也不再自信清除，进入保底）。

## 4. near 的强制清除（回忆 + 补充）

第 04 篇提过 `near` 会设 `forced_clear`。在 `next_action` 里它排在很前面：

```python
if state.forced_clear is not None:
    point, channel = state.forced_clear
    return self._action(state, "clear", point, channel, "near_clear")
```

一旦设了 `forced_clear`，下一次 `next_action` 无论如何先清这一点——**这是最高优先级的
"生死一线"动作**（源就在脚下 5m）。清成功就 `state.forced_clear = None` 复位。
所以 demo 若真遇到 near，会立刻多一个 clear，把流程打断。

## 5. 何时宣告"全部搞定"并退出？

策略不会无事成 `exit`。它会先检查"终端证书是否完整"：

```python
if not remaining:                       # 无待处理频道
    if state.cleared | state.absent != set(range(1,21)):
        raise RuntimeError("频道终止证书不完整。")
    state.phase = "exit"                # 1~20 全覆盖 → 退出
    return None
```

**"证书完整"的意思是**：20 个频道里，清掉的清掉了、判无源的判无源了、一个不落。
只要还有落单的频道，策略就认为没完成、继续 —— 或者直接报错（因为这是逻辑漏洞）。

demo 末尾：

```python
cleared = {3}
absent  = {1,2,4,...,20}      # 并集正好 = {1..20}
```

于是 `cleared | absent == set(range(1,21))` 成立 → `next_action` 返回 `exit`，
主循环看到 exit 被接受，返回 `RunSummary`，整套比赛结束。

`exit` 在 `apply_response` 里简单标记 `state.exited = True`；主循环据此立即组装 summary：
除了动作清单，还有 `cleared_channels`、`absent_channels`、`virtual_time_s`、
`exit_reason="user_exit"`。这些字段正是 demo JSON 的内容（下一篇详解）。

## 6. 万一卡住？（防御性报错）

代码里刻意放了几个看似"多余的"报错：

```python
raise RuntimeError("对未发现频道执行了清除。")
raise RuntimeError("near 后清除失败，规则或实现不一致。")
raise RuntimeError("频道X有限清除保底耗尽。")
raise RuntimeError("频道终止证书不完整。")
```

它们不是要"正常出现"，而是**擂台上的底线**：如果状态机逻辑出了 bug、走到了不该走的
死角，立即把程序停掉并给出明确信息，而不是悄悄做错动作继续跑。**宁可崩，不可错**，
这对竞赛策略这类不容犯错的任务尤为重要。
