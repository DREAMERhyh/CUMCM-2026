# Q3 多源路径规划修改指导说明书

> 本文位于 `src/q3/`，指导对象是 Q3 的多源调度与路线估值。Q2 只负责为单个源生成测点候选，不应因本方案改变其公开 API。

## 1. 文档目的、读者和强制边界

本文面向一个拥有当前仓库全部代码、但没有参与既有代码编写的智能体。该智能体需要同时做到两件事：

1. 能从现有代码准确理解 Q3 的控制流、成本模型和已知局限，为论文描述提供依据；
2. 在用户后续授权后，按照本文实施多源路径优化，而不破坏已经较稳定的单源定位、测量、后验更新和清除逻辑。

本轮只编写本文，不实施路线代码。后续实施必须严格分成两个部分：

- **第一部分：多源服务块 + 最便宜插入 + 2-opt，并与当前策略做同场景配对。**
- **第二部分：缓存 + 有限束搜索。**

第一部分完成并取得离线结果后，实施智能体必须停止，向用户返回完整的配对结果和结论。无论第一部分结果好坏，都不得自动开始第二部分；只有用户明确要求继续，才可实施缓存和有限束搜索。

本文中的“显著下降”默认指有实际意义、跨场景稳定的下降，不等同于小样本统计显著性。第一部分应报告效应量、胜率、P90 和逐场配对差值，由用户决定是否足以进入第二部分。

### 1.1 不得改变的内容

第一部分不得主动改变以下内容：

- Q1/Q2 的公开函数签名、字段、单位和返回语义；
- Q2 的离散基线、连续 FIM 多预算解、Pareto 和顶层推荐生成方式；
- Q3 单源的测量候选池、有限场景后验推演、CVaR 判据和“测量或直接清除”结论；
- `error_deg=1.005`、27 m 清除网格、19.9 m 证书清除阈值；
- 每源专用细化上限 5 次、停滞判据、清除失败条件复测；
- 固定 7 点扫描和保证接收顺便测量；
- 每源顺便测量上限 3 次；
- 每次滚动评价 1 s 真实墙钟软截止；
- Q4 对联合批测、清除失败复测和 Q3 滚动评价保持关闭的隔离设置；
- 官方模拟器协议、动作字段和虚拟时间定义。

如果实施中发现必须改变上述任一项，应停止并单独向用户说明影响，不能把它夹带在路径优化中。

## 2. 为什么优先优化多源路径

用户提供的现场日志为：

`output/sim/q3_20260912-023543-994488.jsonl`

对该日志的已有诊断结果如下：

- 124 条动作记录，成功清除 16 个源；
- 总虚拟时间约 7539.752 s；
- 移动时间约 6853.752 s，占总时间约 90.9%；
- 固定扫描阶段移动约 1800 s；
- 扫描结束后的处理阶段移动约 5053.752 s，占该阶段约 94.7%；
- 处理阶段有 9 次不小于 1 km 的移动，仅这些长跳就约耗时 3375.39 s；
- 只对日志中实际成功清除位置做事后重排，实际顺序的直连距离约 23637 m，而同一批位置的事后最短开路径约 9619 m，对应约 2804 s 的诊断差距。

最后一项使用了事后已知的成功清除位置，只能作为离线下界和根因证据，不能写成在线可达到的保证。但这些数字共同说明：单源定位即使继续小幅改进，也很难抵消跨源长距离折返；多源处理顺序应当是当前最高优先级。

参数“顺便测量最多 3 次”和当时的“滚动软截止 1 s”是在该日志之后调整的，因此该日志不能作为最新参数的正式性能成绩。2026-09-12 滚动软截止又统一改为 3 s，按用户要求尚未重跑。

## 3. 当前代码架构与核心控制流

### 3.1 运行层

离线与正式运行都遵循同一基本调用关系：

```text
runtime.runner.run_policy / sim.live_runner.run_live_policy
    -> policy.next_action(state)
    -> client.execute(action)
    -> policy.apply_response(state, action, response)
    -> 下一轮
```

`next_action` 只产生一个动作；`apply_response` 接收该动作的真实结果并更新状态。因此，任何全局路线都只能是基于当前后验的滚动计划，不能一次性冻结到任务结束。每次测量、清除成功、清除失败或联合批测结束后，都可能需要重新规划。

### 3.2 关键状态

`src/q3/policy.py` 中有两个核心数据结构：

- `SourceTrack`：保存单个频道的观测、当前后验区域、细化次数、停滞次数、清除网格进度、失败清除点、顺便测量次数和最近滚动决策。
- `Q3State`：保存机器人位置、当前频道、阶段、已发现源、已清除频道、扫描进度、待执行动作和同点联合批测进度。

多源路线规划必须只读取这些状态，或增加纯内部、可重建的路线缓存。不能把预测状态当成已经发生的真实状态写回 `SourceTrack` 或 `Q3State`。

### 3.3 扫描阶段

`Q3Policy._scan_action` 使用 `ring7()` 的 7 个固定站完成全区域发现：

1. 在每个固定站依次检查尚未发现的频道；
2. 本站未知频道扫描结束后，调用 `_prepare_scan_batch`；
3. 对已发现、尚可顺便测量且本站对其整个后验区域保证接收的源追加测量；
4. 扫描阶段和扫描后的联合测量共用每源 3 次顺便测量上限；
5. 扫描完成后进入 `phase="resolve"`。

路线优化不得打断固定扫描路线。历史上“每个扫描站后立刻离开去处理局部源”的交错策略已被离线结果否定，原因正是额外往返。

### 3.4 当前 resolve 阶段的真实优先级

`Q3Policy._resolve_action` 当前按以下顺序工作：

```text
若正在执行联合批测：继续完成同点批测
若没有剩余源：退出
若存在清除失败后的待判断复测：先在当前点处理
若存在半径 <= 19.9 m 的证书源：选择离当前位置最近的证书中心清除
若允许自适应细化和联合批测：调用 _joint_plan 比较所有可细化源
若没有选择出测量目标：回退到 remaining[0]，即最小频道号
对该源继续单源细化，或生成/继续其 27 m 清除网格
```

这里有三个需要保留的局部优先事件：

- `forced_clear`：测量返回 `near` 后必须立即清除，由 `next_action` 在 resolve 之前处理；
- 已开始的同点联合批测：机器人已经到达目标点，应完成批次，避免重新移动；
- 清除失败后的同点复测判断：它利用当前位置，不应先离开再回来。

多源路线规划应插入在这些局部事件之后，用来替换“接下来优先处理哪个源”的选择，不能覆盖这些立即事件。

### 3.5 当前单源候选生成

`Q3Policy._refinement_plan` 调用：

```text
q2.planner.plan_measurement(
    track.region,
    track.observations,
    current_position=state.position,
    current_channel=state.current_channel,
    target_channel=track.channel,
    config=policy.q2_config,
)
```

Q2 返回的主要候选包括：

- 顶层混合推荐 `plan["selected"]`；
- 离散基线 `plan["baseline"]["selected"]`；
- 连续 FIM 推荐及多个时间预算候选；
- Pareto 前沿；
- 原离散保证接收候选；
- 保证接收区域代表点。

`q3.rolling_time.extract_q2_candidate_points` 对上述点去重，再只保留对当前后验区域整体保证接收的点，默认最多 12 个。默认 `rolling_time_mode="scenario"` 时，`prefer_continuous_fim` 不决定最终点；它只在关闭滚动模式时生效。

### 3.6 当前单源滚动评价

`Q3Policy._rolling_decision` 构造其他活动源后验包围圆中心列表，传给 `q3.rolling_time.evaluate_total_time_decision`。

对当前源的每个候选测点，现有计算链是：

```text
extract_q2_candidate_points
    -> evaluate_candidate
        -> representative_points：最多 4 个源位置场景
        -> 每个场景枚举 -1.005° / 0° / +1.005°
        -> _posterior_branch：构造测后后验
        -> posterior_clear_points：生成 27 m 覆盖网格
        -> nearest_neighbor_order：单源网格访问顺序
        -> clear_plan_cost：单源清除成本 + 一步续程
    -> risk_summary：mean / P90 / CVaR / worst
    -> 与立即清除成本比较
```

当前默认使用 90% CVaR，只有预计总成本加 10 s 余量仍低于立即清除才测量。每次单源滚动评价有 1 s 软截止：已有完整候选则返回 `partial` 中的最好结果，一个完整候选都没有则安全回退清除。

### 3.7 当前清除路线和时间函数

`src/q3/adaptive.py`：

- `posterior_clear_points(region)`：用 27 m 方格覆盖当前有界后验多边形；理论覆盖半径约 19.092 m，小于 20 m 清除半径。
- `nearest_neighbor_order(points, start)`：从给定起点以最近邻顺序遍历清除点。
- `worst_case_clear_cost(points, start)`：假定源在最后一点才成功，计入移动、每点 3 s 光学清除和最后 2 s 激光清除。

`src/q3/rolling_time.py`：

- `clear_plan_cost(region, start, continuation_points)`：重新生成清除点和最近邻路线，返回单源清除成本、路线终点，并附加“终点到最近其他源中心”的一次续程时间。

`src/q3/joint.py`：

- `direct_clear_cost`：当前后验网格全部清除的保守成本；
- `fixed_point_evaluation`：机器人已在某点时，评价对另一个频道顺便测量；
- `marginal_saving`：用半径平方缩放代理估算顺便测量收益。

`src/common/time_model.py` 是唯一应复用的动作时间定义：

- 测量：移动距离 / 5 + 必要时切换频道 1 s + 测量 5 s；
- 清除：移动距离 / 5 + 光学 3 s；成功时再加激光 2 s。

路线代码不得复制一套不同的速度或动作常数。

### 3.8 当前所谓“多源处理”实际上只到一步前瞻

现有多源逻辑有两层：

1. `clear_plan_cost` 把当前源清除路线终点连接到最近的另一个源中心；
2. `_joint_plan` 为每个可细化源生成一个有效测量方案，最终按以下键选择：

```text
目标测量动作时间最小
-> 同点可批测频道更多
-> 预计节省更多
-> 频道号更小
```

这并不是完整路径规划，原因是：

- 只估计“当前源之后的一跳”，没有安排所有剩余源的顺序；
- 下一跳目标是源后验中心，不是该源真正的测量入口或清除入口；
- 当前源路线终点会随测量结果和清除网格改变；
- `_joint_plan` 最终仍主要按下一次测量动作时间选目标；
- `_joint_plan` 没有可用测量方案时，代码回退到 `remaining[0]`，容易按频道号产生跨场跳跃。

因此，新的路径层必须把每个源的“进入位置—本地处理—离开位置”显式建模，而不是继续在最近中心距离上叠加权重。

### 3.9 当前离线基准框架

`tests/q3/benchmark_adaptive.py::generate_cases` 用固定种子生成 10–16 个全向源，频道从 1–20 随机抽取，位置在半径 1800 m 圆内，接收半径均匀取 1000–1500 m。

`tests/q3/benchmark_rolling_time.py` 已提供可复用框架：

- `InstrumentedPolicy` 记录动作模式、滚动决策及预测误差；
- `_time_breakdown` 按相同动作模型重算移动、切频、测量、光学和激光时间；
- `_run_one` 在同一 `FakeSimulator` 规则下运行一个策略—场景组合；
- `_summary` 汇总完成率、均值、中位数、P90、最坏值、动作数、真实墙钟和移动距离；
- `_comparison` 做逐场配对，检查额外未完成场景、均值、胜率和 P90；
- 当前默认滚动软截止为 3 s；本文已有路线结果仍来自旧 1 s 配置。

路线实验应复用这些统计口径，但建议新建独立的 `tests/q3/benchmark_route.py`，不要覆盖历史滚动基准或历史结果文件。

## 4. 两部分方案之间的关系

完整方案不是同时堆叠四种算法，而是逐级升级：

```text
把源抽象成服务块
    -> 最便宜插入生成一个完整初始顺序
    -> 2-opt 对该顺序做局部改良
    -> 第一部分配对验证并暂停
    -> 用户明确继续
    -> 缓存重复计算
    -> 有限束搜索联合考虑多个顺序/服务选项
```

- 服务块是数据建模层；
- 最便宜插入是初始解构造器；
- 2-opt 是对初始解的改良器；
- 缓存不是优化算法，只是第二部分的计算加速基础；
- 有限束搜索是更昂贵的多步搜索，只有第一部分证明路线方向有效后才值得加入。

## 5. 第一部分：多源服务块 + 最便宜插入 + 2-opt

### 5.1 第一部分目标

只改变“下一步优先处理哪个源”，保持选定源内部的现有决策不变。具体来说：

- 原 Q2/FIM 候选照常生成；
- 原滚动评价仍决定该源测量还是直接清除；
- 原同点批测规则不变；
- 原后验更新、27 m 网格、最近邻单源清除和失败复测不变；
- 路径层只比较不同源的入口、预测出口和连接移动成本；
- 实际只提交当前应执行的动作，收到响应后重新规划。

### 5.2 “服务块”不是一次性执行脚本

服务块是路线估值用的预测摘要，不是必须原子执行到结束的动作列表。原因是测量结果和清除成败会改变后验，后续动作不能提前确定。

建议新建 `src/q3/route.py`，定义私有或内部数据结构 `SourceServiceSpec` / `SourceServiceBlock`。推荐字段如下：

```text
channel                 主源频道
mode                    certified_clear / measure_then_clear / direct_clear
entry_point             预测进入点
exit_point              确定性保守出口代理
entry_action_kind       measure 或 clear
entry_action_channel    首动作频道
batch_channels          若为联合测量，记录同点频道顺序
local_cost_s            不含前驱到入口移动的本地预计成本
route_points            用于估值的当前后验清除点顺序
source_version          当前源状态指纹，防止复用过期块
diagnostics             候选来源、半径、滚动状态等，仅用于测试/日志
```

第一部分使用确定性、保守的出口代理，不在这里传播完整场景树：

- 证书清除：入口和出口都是包围圆中心；
- 直接清除：从预测前驱位置出发，对当前 27 m 网格调用现有 `nearest_neighbor_order`，入口为首清除点，出口为最后清除点；
- 测量后清除：入口是现有滚动评价选出的测点；为了只做源顺序优化，出口代理可取“从该测点出发遍历当前后验网格”的最后一点。这是保守代理，真实测量后网格通常会收缩；执行时仍等待真实测量并重新规划。

不要在第一部分为了得到更漂亮的服务块而改变单源测点或清除点集合。

### 5.3 服务块应按“预测进入状态”物化

直接清除的最近邻顺序依赖进入位置，因此不能为每个源永久固定一个入口和出口。建议区分：

- `SourceServiceSpec`：从当前真实后验生成，不依赖路线前驱；
- `materialize_service_block(spec, incoming_position, incoming_channel)`：给定预测前驱状态后，生成该位置下的入口、网格顺序、出口和成本。

对一条候选源顺序做估值时，从机器人当前真实位置和频道开始，依次物化每个块，把上一个块的预测出口作为下一个块的进入位置。这样最便宜插入和 2-opt 比较的是完整开放路线，而不是只比较源中心距离。

对测量块，测点是固定入口；前驱只改变到该测点的移动和切频成本。对直接清除块，前驱还会改变当前 `nearest_neighbor_order` 的顺序和出口。

### 5.4 服务模式必须来自现有单源结论

不要另写一套“是否测量”的规则。建议把当前 `_joint_plan` 拆成两个职责，但保持计算内容不变：

1. `_build_joint_options(state, remaining)`：为每个可细化源生成当前已有的 Q2 计划、滚动结论、目标测点和可顺便测量频道；
2. `_select_joint_option(...)`：当前策略的选择器，保留作为关闭路线模式或路线失败时的安全回退。

服务规格生成规则：

- 当前单源滚动结论为 `measure`：生成 `measure_then_clear` 规格，保存现有选中测点和联合批测信息；
- 当前单源滚动结论为 `clear`、源不可继续细化或已停止细化：生成 `direct_clear` 规格；
- 半径不超过 19.9 m 且证书未失败：生成 `certified_clear` 规格；
- 存在 `forced_clear`、待完成联合批测或失败点同点复测时，不调用全局排序，先处理这些局部强制事件。

切勿把“没有被本轮路线选中”误写成 `refinement_stopped=True`。只有该源自己的现有细化判据明确拒绝继续测量时，才能停止它的细化。

### 5.5 路线成本

建议提供一个纯函数：

```text
evaluate_open_service_route(
    order,
    specs,
    start_position,
    start_channel,
) -> RouteEstimate
```

它按顺序物化服务块，并累计：

- 前一出口到下一入口的移动时间；
- 测量前必要的频道切换时间；
- 测量固定时间；
- 使用现有模型得到的单源本地清除成本；
- 联合批测中已知的额外切频和测量时间。

第一部分的主要排序目标是总预测虚拟时间；平局顺序建议为：

```text
预测总虚拟时间
-> 总移动距离
-> 长跳次数
-> 源频道序列（保证确定性）
```

这里采用开放路线：起点是机器人当前位置，完成最后一个源后不要求返回原点。

### 5.6 最便宜插入

最便宜插入负责从零构造一个完整初始顺序，而不是对最近邻结果继续追加。

建议算法：

1. 对每个剩余源单独估值，选择从当前状态开始增量成本最小者作为第一个块；
2. 对每个尚未插入的源，尝试插入当前序列的所有位置；
3. 每个候选插入都调用 `evaluate_open_service_route` 完整重算，因为直接清除块的入口和出口依赖前驱；
4. 选择使全路线成本增加最少的“源—插入位置”组合；
5. 重复直到所有剩余源进入顺序；
6. 平局时按频道号和插入位置确定性裁决。

剩余源通常只有 10–16 个，第一部分优先保证逻辑正确和可解释，不要为了微小计算节省引入难以验证的增量公式。

### 5.7 2-opt

2-opt 接收最便宜插入的完整开放顺序，尝试反转任意连续片段：

```text
原顺序：A -> C -> B -> D
候选：  A -> B -> C -> D
```

由于服务块入口/出口是有方向的，并且块可能随前驱重新物化，不能直接套用对称 TSP 的两条边差公式。对每次片段反转，应调用 `evaluate_open_service_route` 重算完整路线。

建议采用确定性的最佳改进：

1. 枚举所有 `i < j` 的反转；
2. 找到本轮成本下降最大的候选；
3. 只有下降超过数值容差才接受；
4. 重复到没有改进；
5. 设置独立的有限迭代上限和软截止；若截止，返回当前最好完整路线。

第一部分不要加入随机重启、模拟退火或束搜索，否则无法单独判断“最便宜插入 + 2-opt”的贡献。

### 5.8 接入 `Q3Policy` 的建议方式

建议新增内部开关：

```text
multi_source_route_mode = "off" | "insertion_2opt"
```

为了配对测试，正式默认值是否立即改为开启，应在第一部分结果返回后由用户决定。实现阶段可以在测试策略中显式开启，不应未经结果直接替换正式默认。

建议的 resolve 控制流：

```text
处理 forced_clear / 未完成联合批次 / 失败点同点复测
    -> 为所有剩余源生成现有单源选项和服务规格
    -> 若 route_mode 开启：最便宜插入 + 2-opt 得到优先频道顺序
    -> 取顺序第一个频道
    -> 若该频道现有单源结论是 measure：执行原联合测量动作
    -> 否则：执行该频道现有证书清除或保底清除动作
    -> 收到真实响应
    -> 更新后验/清除状态
    -> 下一轮重新生成路线
```

联合批测仍可把其他频道加入当前测点；批次结束后必须重算服务规格，因为其他源的后验已经变化。

路线规划发生异常、没有得到完整顺序或达到软截止时，必须回退到当前未修改的选择逻辑，不得返回空动作。

### 5.9 第一部分预计修改文件

推荐最小范围：

- 修改 `src/q3/policy.py`：拆分现有联合选项生成与选择，接入路线排序和安全回退；
- 必要时对 `src/q3/rolling_time.py` 增加纯诊断字段，但不得改变原候选排序和 measure/clear 结论；
- 修改 `tests/q3/test_offline.py`：增加纯算法及状态机回归；
- 新建 `tests/q3/benchmark_route.py`：当前策略与第一部分策略的同场景配对；

### 5.10 第一部分必须具备的自动测试

至少覆盖：

1. **开放路线成本**：手工构造 3 个确定性服务块，核对移动与动作时间；
2. **最便宜插入**：构造频道号顺序明显更差的几何布局，确认算法选择短路线；
3. **2-opt 改良**：输入带交叉或明显折返的初始顺序，确认成本严格下降；
4. **确定性**：同一状态重复规划得到同一频道顺序和成本；
5. **不改清除覆盖**：路线开启前后，每个源使用的 27 m 清除点集合相同，只允许源顺序或单源点列起点相关顺序变化；
6. **不改单源决策**：对同一个源和同一个实际进入状态，Q2 候选、选中测点、measure/clear 结论与路线关闭时一致；
7. **不误停其他源**：未被本轮选中的源不能被标记为停止细化；
8. **联合批测兼容**：同点批次完整执行，之后路线重算；
9. **失败清除兼容**：失败后仍先进行现有同点复测判断；
10. **强制 near 清除**：`near` 后仍立即清除，不受全局顺序影响；
11. **超时/异常回退**：路线规划失败时产生与当前策略一致的有限动作；
12. **Q4 回归**：Q4 不启用 Q3 多源路线新分支，现有 Q4 测试必须通过。

完成针对性测试后，还要运行：

```powershell
python -B -m unittest discover -s tests -t . -v
```

自动测试通过只能说明本地实现可运行，不能标记为人工已验证或官方模拟器已测试。

### 5.11 第一部分配对基准

新建的 `benchmark_route.py` 必须让两种策略共享完全相同的案例对象：

- `current`：本次修改前的当前 Q3 行为；
- `insertion_2opt`：仅开启第一部分路线层，其余参数与 `current` 完全相同。

两组必须共同使用：

- 相同源数量、频道、真实位置和接收半径；
- 相同 `error_deg`、FIM 上限、滚动风险口径和 1 s 软截止；
- 相同 27 m 网格；
- 相同每源 3 次顺便测量上限；
- 相同清除失败复测开关；
- 相同最大动作数；
- 相同随机种子和测试进程设置。

不要在配对中同时调整其他参数。若必须调路线算法自己的迭代上限，应先在训练案例选择，再锁定参数去未见验证种子；不得在验证场景上反复调参。

每个场景至少输出：

- 是否完整清除全部真实源；
- 总虚拟时间；
- 总移动距离和移动时间；
- 扫描阶段移动距离；
- resolve 阶段移动距离；
- 跨源移动距离；
- 不小于 1 km 的长跳次数及距离；
- 测量、切频、光学和激光时间；
- 动作数；
- 路线规划调用次数、平均/最大真实墙钟；
- 路线规划 `ok/partial/fallback/error` 计数；
- 实际源处理顺序；
- 每次规划的预测路线成本及之后实现的局部成本，便于检查估值偏差。

“跨源移动”需要在基准中显式定义。建议让测试用 `InstrumentedPolicy` 为每个 resolve 动作记录主服务源；当相邻非零移动属于不同主服务源时，将该距离计入跨源移动。同点 `joint_extra` 的频道切换不能误算成跨源移动。

汇总至少包括：

- 完成场景数；
- 平均/中位/P90/最坏总虚拟时间；
- 平均 resolve 移动距离；
- 平均跨源移动距离；
- 平均长跳次数；
- 逐场 `insertion_2opt - current` 差值；
- 胜场数与胜率；
- P90 是否恶化；
- 真实计算时间增量。

最低安全判据：

- 新策略不能比当前策略多出未完整清除场景；
- 不得破坏动作有限性和安全退出；
- 全项目自动测试通过。

路线效果判据建议同时观察：

- 配对平均 resolve/跨源移动距离是否下降；
- 至少一半可比场景是否下降；
- P90 总虚拟时间是否不恶化；
- 总虚拟时间均值是否随移动下降而下降；
- 计算墙钟是否仍有足够的正式测试安全余量。

这些指标不是第二部分的自动授权条件。

## 6. 第二部分：缓存 + 有限束搜索

### 6.1 启动门槛

第二部分的唯一启动条件是：

- 第一部分已经实现并完成同场景配对；
- 结果已经返回用户；
- 用户随后明确要求继续缓存和有限束搜索。

第一部分即使所有判据都通过，也不得自动继续。

### 6.2 为什么先缓存

有限束搜索会重复评价相同源状态、候选测点、测后后验和清除网格。如果没有缓存，增加搜索宽度很容易耗尽 1 s 滚动软截止或正式测试现实时间。

缓存应当先作为不改变数值结果的纯性能优化实现，并单独测试命中与失效。

### 6.3 建议缓存层级

可按以下顺序加入：

1. **后验/源状态指纹**

   包含频道、排序后的观测位置与角度、后验平面/顶点、细化和停止标志、失败清除点、清除网格索引。浮点数必须采用统一量化精度。

2. **Q2 规划缓存**

   键至少包含源状态指纹、机器人当前位置、当前频道和完整 `Q2Config`。当前位置会影响动作时间，不能遗漏。

3. **清除网格缓存**

   键包含后验区域指纹和网格间距。只缓存点集合，不缓存依赖起点的最近邻顺序。

4. **清除路线缓存**

   键包含网格指纹和量化后的起点。返回有序点列、距离、成本和出口。

5. **候选—场景测后结果缓存**

   键包含源状态指纹、候选测点、源位置场景、误差端点和配置；返回测后后验、清除点和路线信息。

6. **服务规格/块缓存**

   键包含全部活动源版本、当前机器人状态、风险口径和路线配置。

任何影响成本或几何的字段遗漏都会产生危险的过期复用。宁可降低命中率，也不能用不完整键换速度。

建议缓存有明确容量上限，并记录：命中数、未命中数、失效数、条目数和节省的真实墙钟估计。不要让缓存跨独立模拟场景共享可变状态。

### 6.4 有限束搜索的状态

束搜索节点建议包含：

```text
已安排的源序列
剩余源集合
预测当前位置
预测当前频道
累计虚拟成本 g
剩余成本下界 h
总排序值 g + h
已选服务模式/候选点
来源节点和诊断信息
```

第二部分才允许每个源保留多个服务选项，例如：

- 直接清除；
- 当前滚动评价选中的测点；
- Q2 顶层/离散/连续/Pareto 中少量经保证接收筛选的测点。

但最终执行前仍必须通过现有单源安全条件，不能因束搜索评分较低而执行不保证接收的点。

### 6.5 束搜索扩展与剪枝

建议流程：

1. 根节点为当前真实位置、当前频道和全部剩余源；
2. 每层从每个节点选择若干“下一源—服务选项”扩展；
3. 使用服务块成本更新 `g`；
4. `h` 使用乐观但安全的简单下界，例如剩余入口点的最小生成树移动下界加不可避免的固定动作时间；
5. 每层按确定性键保留有限宽度；
6. 达到软截止时返回已经形成的最好完整顺序；
7. 若没有完整束搜索解，回退到第一部分的“最便宜插入 + 2-opt”；
8. 若第一部分也失败，再回退当前旧选择器。

回退层级必须是：

```text
有限束搜索
    -> 第一部分 insertion + 2-opt
    -> 当前既有一步策略
```

不能因束搜索超时直接产生空动作或不完整动作序列。

束宽、每源选项数、搜索深度和路线软截止都必须作为内部配置记录到基准结果。初始值可以保守设置，但最终值应在训练案例选择并锁定后再进入未见验证场景。

### 6.6 第二部分测试

除第一部分全部测试外，还要覆盖：

- 缓存开启/关闭时数值结果完全一致；
- 任一观测、位置、频道、活动源集合或配置变化都会使相关缓存失效；
- 缓存容量上限和清理不改变结果；
- 束宽 1 的行为可解释且确定；
- 增大束宽不会返回比同一搜索已完成解更差的内部最优值；
- 超时有完整解时返回最好完整解；
- 超时无完整解时回退第一部分；
- 第一部分异常时仍回退当前策略；
- Q4 不进入新缓存/束搜索分支；
- 全项目测试通过。

### 6.7 第二部分基准

至少做三策略同场景配对：

- `current`；
- `insertion_2opt`；
- `beam_cached`。

必须沿用第一部分锁定的验证场景，不得因为结果不好更换种子。另用训练场景选择束宽等参数，再在未见验证场景报告。

第二部分除了第一部分的全部指标，还应汇报：

- 缓存命中率；
- 候选/场景完整评价数量；
- `ok/partial/fallback` 比例；
- 束搜索平均实际扩展节点数；
- 平均/最大路线规划墙钟；
- 相对第一部分新增的总虚拟时间收益；
- 相对第一部分新增的计算代价。

若 `beam_cached` 未稳定优于 `insertion_2opt`，应保留第一部分作为正式候选，不得因为第二部分更复杂就默认采用。

## 8. 论文描述口径

如果后续智能体需要据此编写论文，应使用以下准确表述：

- 当前方法是“有限场景下的滚动多源启发式规划”，不是全局最优算法；
- 服务块把每个源抽象为入口、本地处理成本和出口的宏观任务；
- 最便宜插入构造开放访问序列，2-opt 消除局部折返；
- 实际系统每次只执行一个确定动作，并在真实响应后重新规划，因此具有滚动反馈；
- 单源定位仍由 Q2 候选、集合后验和 Q3 的 CVaR 总时间评价完成；
- 27 m 网格提供几何覆盖保证，路线层只改变访问顺序，不改变覆盖点集合；
- 离线配对只能说明固定生成分布和有限样本下的表现，不能声称全局最优概率；
- 日志的事后最短路径只是诊断下界，不能作为在线算法成绩；
- 任何性能数字必须注明网格间距、顺便测量上限、FIM 上限、滚动截止、种子和案例数。

若第二部分尚未获得用户授权或尚未实施，论文中不得把缓存、束搜索或其预期收益写成已完成工作。

## 9. 常见错误与审查重点

- 不要把“源中心最近”继续包装成完整路径规划；
- 不要让路径层重新决定 FIM 点，第一部分只排序源；
- 不要一次提交整条预测动作序列；
- 不要在未收到测量结果前写入预测后验；
- 不要因某源本轮未被选中就停止其细化；
- 不要漏计频道切换、5 s 测量、3 s 光学和成功时 2 s 激光；
- 不要要求最后返回原点；
- 不要让同点联合批测产生虚假的跨源移动；
- 不要把 Q4 的定向源问题套用全向源服务块保证；
- 不要覆盖旧基准结果；
- 不要在验证种子上调路线参数；
- 不要把自动测试通过写成官方模拟器已验证；
