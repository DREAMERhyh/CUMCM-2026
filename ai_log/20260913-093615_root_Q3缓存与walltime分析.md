# AI 使用记录：Q3缓存与walltime分析

## 输入

```text
当前Q3计算上限设置为3s，wall-time很大，之前的缓存单独开启能否减少walltime
```

## 运行结果

只读核对了 Q3 策略、滚动估值、缓存实现、在线 CLI、历史路线基准与 `solution/output/sim/3-opt-3/` 的 5 份正式日志。确认当前 3 s 是“每个候选源的一次滚动评价上限”，一次 `next_action` 会遍历所有可细化源，因此总规划时间可累加为“源数 × 3 s”，并非单动作总计 3 s。5 份日志中相邻请求间隔至少 2.5 s 的 123 段合计 1813.84 s，占全部相邻请求间隔 1843.12 s 的约 98.4%，最大单段 39.95 s，说明 wall-time 主要由多源串行滚动评价造成。

核心 `Q3Policy` 已支持在 `insertion_2opt` 下单独设置 `computation_cache_mode="bounded"`，缓存键包含后验、观测、机器人位置、频道和配置，不会拿旧观测替代新状态。但本地与在线 CLI 尚未暴露该独立开关；只有选择 `beam_cached` 时会自动启用缓存。历史 4 场景 `beam_cached` 数据的总命中率约 77.9%，但命中主要来自 `service_block`（约 96%），昂贵的 `candidate_scenario` 和 `q2_plan` 命中率均为 0，`clear_route` 约 1%，且该组同时更换了路线算法，不能作为“缓存单独开启”的干净对照。因此结论是：单独开启缓存应能小幅降低 wall-time，尤其减少同一状态下重复的服务块/网格计算，但不太可能根治目前 10--40 s 的单动作停顿；更有效的控制是把 3 s 改成整次多源选择共享的总预算，或先筛少量源再做滚动评价。未修改策略代码，未运行新性能基准。
